# 博客写作工作流

## 恢复上下文与确定范围

1. 读取博客根目录的 `AGENTS.md` 和 `readme.md`，将其作为目录、命令、Git、验证和发布流程的依据，不在本 skill 重复维护这些规则。
2. 从用户提供的资料定位相关笔记、论文、代码或实验记录；需要 Obsidian 时定位 vault 并读取该位置适用的指令。不要硬编码个人盘符或目录结构；只读取相关资料，不因未提供 Obsidian 笔记而阻塞可独立进行的写作。
3. 查找已有文章工作笔记、Typst 草稿和素材；编辑前检查当前分支与工作区。保留用户修改，按仓库规则使用工作分支。
   恢复写作时交叉检查工作笔记、实际 Typst 文件和 Git 差异；记录过时时以实际文件为准，在获准维护的范围内修正记录。不要仅凭旧笔记重复已完成的工作，也不要将本地提交视为已经上线。
4. 结合当前请求和此前明确决定选择进入阶段。不要反复询问已确定的读者、范围或语言偏好；只对实质影响结果且无法合理推断的信息提问。

| 用户意图 | 执行范围 |
| --- | --- |
| 讨论选题、流程或结构 | 阅读资料并提出方案，不自动创建或修改文件 |
| 写作、续写或按意见修改 | 在现有决定基础上编辑，必要时补研究 |
| 审阅或诊断文章 | 报告有依据的问题和建议；用户要求修改时再编辑 |
| 提交或推送 | 仅执行获准的 Git 操作，不解释为发布授权 |
| 明确发布某篇文章 | 按根目录发布流程检查范围、验证、发布与线上结果 |

## 维护位置

- 在 Obsidian 保存来源、完整推导、实验记录、知识关系和未决问题。允许一个主题支持多篇文章，也允许一篇文章引用多个主题。
- 用一份文章工作笔记保存读者、问题、范围、大纲、证据缺口和编辑决定。需要持久化写作进度时，读取并按需采用 [工作笔记模板](assets/article-worknote.md)，按下节固定目录存放，复用记录，不重复建卡。
- 进入 Typst 后只在 Blog 维护正文。Obsidian 记录文章路径和发布地址，不同步 Markdown 全文。
- 记录影响后续写作的决定，不复制聊天记录。不要为了填满模板而编造信息或制造研究任务。

## 文章工作笔记目录

- 在定位到的 vault 内使用 `文章撰写/Blog/` 作为本博客的写作专区；工作笔记统一放在 `文章撰写/Blog/文章/`。遵循该目录适用的指令。不要移动或改写 `文章撰写/` 中已有的旧文章，也不要把编辑过程放入 `wiki/syntheses/`。
- 每篇新文章使用独立目录 `文章/<稳定工作标识>/`，默认只创建其中的 `工作笔记.md`。初次建卡选简短且唯一的英文标识，通常与预期 article-id 一致；已有笔记保持路径，不自动迁移。标题、文章阶段或博客分类变化不触发改名或移动。正式 slug 尚未确定时允许 `blog_slug` 留空，通过 `article_path` 记录最终映射。
- 工作笔记集中保存文章定位、大纲与证据、待验证问题、编辑决定、审阅与修改、进度与下一步。默认不拆出大纲、待办、审阅或 Markdown 草稿文件；只有内容较长且需要独立使用时才拆分，并从工作笔记链接过去。
- 有文章专属参考截图、图示构思或可编辑图稿时，按需创建同目录的 `素材/`，没有实际材料时不创建空目录。发布图片放在博客的 `public/images/articles/<slug>/`；可编辑源稿选择一个主要维护位置，记录源稿与发布图片的对应关系，不双份编辑。已有研究笔记和实验资料留在原处，只做链接引用。
- 所有文章的工作笔记同名，内部链接应包含文章目录，例如 `[[文章撰写/Blog/文章/tangent-space/工作笔记|Tangent Space 工作笔记]]`，避免短链接歧义。
- 创建前按 `type: blog-article`、工作标识、标题、源笔记和 `article_path` 查重。遇到同名但不同文章时选另一个明确标识，不覆盖。系列中的每篇独立文章各建一份，使用相同 `series` 属性关联。
- 以工作笔记 frontmatter 为阶段和关联信息的唯一记录处。使用 `status` 表达选题、组织论证、写作、审阅、待发布、已发布、暂停或放弃；不按状态或年份分文件夹。用 `created`、`updated` 记录工作笔记日期，不代替文章发布日期。
- 需要总览时在专区根目录建立 `文章总览.base`，递归收集 `文章/` 下 `type: blog-article` 的工作笔记，兼容已有平铺笔记，排除素材和辅助文件。展示标题、状态、更新时间、系列及文章路径，按状态分组。创建前使用可用的 Obsidian Bases 技能并核验语法；不依赖 Dataview，也不再手工维护一份重复的状态表。
- 仅讨论时提出上述路径即可，不自动写入 vault。获准建立写作记录后再创建所需目录和工作笔记；没有文章时不创建占位卡片。总览与具体工作笔记可按需建立，不因缺少总览而阻塞文章写作。

目录示例（素材按需创建）：

```text
文章撰写/Blog/
├── 文章总览.base
└── 文章/
    └── tangent-space/
        ├── 工作笔记.md
        └── 素材/
            ├── 参数化示意.excalidraw
            └── 图示参考.png
```

## 选题与组织论证

1. 提炼读者问题、必要前置知识和读完能得到的结论。按问题决定篇幅，不默认短文，也不默认完整覆盖主题笔记。
2. 明确本篇边界和不展开的支线。范围有实质分歧时给出少量方案与推荐理由；已有明确要求时直接采用。
3. 为大纲的关键结论关联证据，区分数学推导、源码观察、实验结果和解释。不要将 synthesis 中的链接视为已经核验的来源。
4. 对影响结论的缺口选择补证、收窄表述或移出本篇。依赖特定实现行为时核验版本与源码；声称实测差异时提供相应实验。不得编造引用、数据或作者经历。
5. 当读者、问题、范围和论证顺序足够明确时进入写作。允许返回研究，无需清空主题笔记的全部待办。
6. 新发现的问题不影响本篇结论时，记作后续选题，不自动扩展正文。新增章节若改变核心问题或目标读者，先与用户重新确定范围，再执行依赖该决定的改写。

## 阶段与文章演变

- 用 `status` 表示当前工作阶段，用 `published_url` 表示已有线上版本；两者独立。已发布文章进入修订时将阶段改为写作或审阅，保留发布地址，并在进度中说明当前修改尚未上线。
- 主线与范围明确后进入写作；完整草稿形成后进入审阅；内容审阅与草稿预览完成、影响核心结论的问题已解决或妥善收窄后，才标为待发布。待发布仍须完成获授权后的生产验收。
- 只有当前版本部署与线上检查均成功才标为已发布；失败时保留实际阶段并记录失败环节。暂停或放弃仅表达工作安排，不移动目录或删除已有记录。
- 阶段字段不是授权。根据当前请求及会话中仍适用于此次范围的明确授权决定提交、推送或发布；不得从待发布状态或历史发布记录推断新修订的上线许可。
- 一篇拆为多篇时分别建立工作笔记，在原记录说明去向并链接新记录；合并时指定主记录，其他记录注明合并目标并停止重复维护。保留原记录，按实际安排设置状态，不自动发布、删除或重定向已有线上文章。

## 撰写与续写

1. 按 `readme.md` 创建新文章，已有草稿则续写。保留默认草稿状态，检查日期、slug 和统一标签。
2. 改写为面向读者的叙事，解释必要前提，统一符号、术语和坐标约定。避免机械搬运章节或先写完整 Markdown 中间稿。
3. 将内部双链转换为独立可理解的说明、已有公开文章链接或已核验的原始来源。不要输出读者无法访问的 vault 路径，不自动公开内部笔记或素材。
4. 用图、公式和最小例子解决具体理解难点；遵守仓库素材路径、来源与图注规范。不顺带修改模板或站点功能。
   外部图和改绘图记录原始来源、作者及许可或其他使用依据；无法确定时记录缺口，不假定标注来源就等于允许使用。生成图记录源文件或生成方法及必要参数，确保可修改或重建。简单记录放在工作笔记，不另建素材清单文件。
5. 需要页面反馈时启动开发预览，报告实际地址。结构稳定前避免大量逐句润色；局部修改请求保持局部范围。
6. 关键事实无法核验时记录其影响，完成不依赖该问题的工作，不将其写成确定结论。

## 审阅与发布

1. 审阅前读取 [审阅指南](references/review-guide.md)。依次检查内容正确性、论证结构、语言和实际页面，按请求选取层次。
2. 按根目录要求构建和测试。草稿被生产构建排除时，测试通过不能证明草稿正确；用开发预览直接检查新正文、图和公式。
3. 获明确发布授权后执行根目录发布流程，检查获准文章的生产页面、canonical、RSS 和 sitemap。部署与线上检查都成功后才报告发布成功。
4. 提交不等于推送；认可文案不等于发布授权。遵守仓库的草稿与公开资源隐私约定。

## 已发布文章修订

- 区分措辞或排版修正与影响结论的改动。重要纠错在公开文章中保留简短修订说明，说明日期、改正内容和对原结论的影响；工作笔记保留必要证据及编辑决定。
- 保持原发布日期、slug 和路径稳定。工作笔记的 `updated` 只表示笔记更新，不充当文章修订日期；公开修订日期使用现有站点支持的字段或正文说明，不擅自新增不受支持的元数据。
- 修订在工作分支进行，不通过将已上线文章改为 `draft: true` 隐藏修订。审阅受影响的结论、图示和链接，同时完成根目录要求的构建与测试；获本次发布授权后再执行发布流程。

## 回流与交接

- 在已授权的知识维护范围内，将写作中新发现或纠正的结论及来源回填相关 Obsidian 笔记；纯措辞和排版修改留在 Blog。未授权 vault 写入时报告建议回填项。
- 有工作笔记且已获维护授权时，在实质进展后更新阶段、路径、关键决定、剩余问题和下一步；用一句话记录当前做到哪里，必要时附分支、提交及验证所对应版本。发布后记录实际线上地址及已核验的发布版本。不提前标记完成或虚构验证结果。
- 将工作笔记作为恢复工作的检查点，不逐轮复制对话或记录每次措辞修改。问题解决后保留必要结论与证据，移除失效待办；无实质变化时不为更新时间而改写笔记。
- 交接时报告文件、实质修改、实际验证及范围、未决问题和下一步。区分完成草稿、本地提交、推送与上线。
